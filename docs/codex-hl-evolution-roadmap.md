# Codex HL Evolution Harness Roadmap

## 一句话结论

Codex HL Evolution Harness 是挂在 Codex 外面的高层学习壳层。它先把真实 Civ6 对局完整记录下来，再从真实失败里沉淀资产和验证场景，最后走向自动合并、自动回滚、自动审计。

当前近期目标不是自动学习，而是把 Phase 1 的观测记录做扎实。

## 不做什么

- 不是 Civ6 专项 RL。
- 不训练模型权重。
- 不把 `test 1` 单个存档当成产品中心。
- Phase 1 不判断策略好坏，只负责完整观测。
- 早期不做复杂 dashboard。
- 不让未验证的候选策略进入主线。
- 不把胜率作为早期唯一指标。

## 总体结构

路线图采用“阶段总览 + 三线展开”的结构。

阶段从 Phase 0 走到远期 L5：

| 阶段 | 核心目标 | 主要产出 |
| --- | --- | --- |
| Phase 0 | 对齐边界和词汇 | 统一 episode、decision atom、asset、scenario、merge、rollback 等概念 |
| Phase 1 | 完整记录一局 | episode 目录、原始工具调用、回合状态、关键决策、存档关联、短跑验收报告 |
| Phase 2 | 从真实记录里标失败 | 失败样例、失败分类、回归样例雏形 |
| Phase 3 | 建立资产体系 | prompt、playbook、tool policy、低信任 memory 的版本化管理 |
| Phase 4 | 形成候选改进流程 | 候选来源、验证计划、证据包、可回滚资产变更 |
| Phase 5 | 从真实失败沉淀验证集 | regression 场景池、多场景验证、退化检查 |
| L4/L5 | 自动验证、自动合并、自动回滚、自动审计 | 系统自动 merge，退化时自动 rollback，并产出审计报告 |

每个阶段都按三条线展开：

- 记录系统：能不能完整知道发生了什么。
- 资产系统：prompt、playbook、tool policy、memory 如何被管理和演进。
- 验证系统：如何判断结果真的变好。

最终目标不是让人长期审批策略合并。系统成熟后，低风险和已验证的策略资产应该自动合并；人类主要查看审计报告、异常告警和回滚样例。

## 六类能力主轴

所有失败分类、资产组织、验证覆盖都围绕六类能力展开：

1. planning
2. execution
3. memory/state
4. tool grounding
5. verification
6. recovery

这六类不是单独的标签，而是贯穿三条线：

| 能力维度 | 失败分类中怎么用 | 资产系统中怎么用 | 验证系统中怎么用 |
| --- | --- | --- | --- |
| planning | 是否目标错、顺序错、计划过粗 | playbook、prompt 中的规划规则 | 是否能在相似局面做出更好计划 |
| execution | 是否动作执行错、漏执行、执行顺序错 | tool policy、操作流程 | 是否能稳定执行计划 |
| memory/state | 是否记错历史、误用旧信息、忽略当前状态 | memory 低信任引用规则、state snapshot 规则 | 是否会被错误记忆或过期状态带偏 |
| tool grounding | 是否没查工具、查错工具、误读工具结果 | tool policy、状态检查清单 | 是否能在决策前拿到足够证据 |
| verification | 是否没有检查结果、误判成功 | verifier、验收规则、报告模板 | 是否能发现策略退化 |
| recovery | 是否失败后不会补救、不会回滚 | recovery playbook、rollback policy | 是否能从错误中恢复并保留证据 |

## 结果指标

最终证明系统变强，最硬的证据是结果变好。

早期主指标先使用 T50，因为它足够快，适合暴露问题和比较改动。第一版 T50 主指标只看三项：

- 城市数
- 科技进度
- 文化/市政进度

军力、安全风险、金币、信仰、外交关系等可以作为补充指标，但第一版不作为主指标。

后续阶段可以逐步加入 T100、终局胜率、多场景表现和退化率。

## Phase 0：边界和词汇

目标：先避免方向画歪。

### 记录系统

定义最小记录单位：

- episode：一局或一段可复盘运行。
- turn snapshot：每回合状态快照。
- decision atom：关键决策原子。
- save link：存档与回合、决策、事件的关联。

Phase 0 不要求跑通真实游戏，只要求团队能用同一套词描述系统。

### 资产系统

定义可进化资产：

- prompt
- playbook
- tool policy
- memory

memory 是低信任资产。它只能作为参考，不能直接决定动作，不能替代当前状态检查，也不能绕过工具确认。

### 验证系统

定义早期验证口径：

- 先看 T50。
- 第一版主指标是城市数、科技进度、文化/市政进度。
- 不靠单个存档证明通用变强。

## Phase 1：完整观测一局

目标：把一局真实 Civ6 对局完整记录下来。

Phase 1 只做观测，不做失败归因，不做 Replay Arena，不生成候选策略改进，不做自动学习闭环。

### 记录系统

Phase 1 合格标准是四类记录都必须落盘：

1. 全部工具调用和返回结果。
2. 每回合状态快照。
3. 关键决策前后的背景、候选动作、选择理由、执行结果。
4. 存档文件和回合、决策、事件的关联。

第一版执行顺序：

1. 先跑 3-5 回合短跑。
2. 生成 HTML 验收报告。
3. 人类验收通过后，再跑到 T50。

短跑报告至少说明：

- 本次 episode 信息。
- 实际跑了几个回合。
- 每回合发生了什么。
- 四类记录是否完整。
- 缺失字段和阻塞问题。
- 是否满足继续 T50 的条件。

### 资产系统

Phase 1 不改资产，只记录本局开始时使用了哪些资产版本。

需要保留 assets snapshot：

- 当前 prompt 版本。
- 当前 playbook 版本。
- 当前 tool policy 版本。
- 当前 memory 引用范围。

### 验证系统

Phase 1 只产出指标，不宣称策略好坏。

T50 后记录：

- 城市数。
- 科技进度。
- 文化/市政进度。
- 重要异常和缺失信息。

## Phase 2：从真实记录里标失败

目标：从真实 episode 中找出失败，而不是预设一套空 taxonomy。

### 记录系统

每个失败都必须能回到证据：

- 哪个 episode。
- 哪个 turn。
- 哪个 decision atom。
- 相关工具调用。
- 相关状态快照。
- 相关存档。

### 资产系统

失败开始按六类能力主轴归类：

- planning
- execution
- memory/state
- tool grounding
- verification
- recovery

如果失败不能映射到现有资产，先记录为 unmapped failure，不强行修改资产。

### 验证系统

真实失败开始沉淀为 regression 场景。

每次事故、退化、误判都应该进入验证场景池，后续用于防止同类问题复发。

## Phase 3：建立资产体系

目标：让系统知道自己能改什么、不能改什么、怎么回滚。

### 记录系统

记录每次资产变化的证据来源：

- 来自哪个失败。
- 关联哪些 episode。
- 关联哪些指标变化。
- 关联哪些人工或自动判断。

### 资产系统

每个资产都要有：

- 资产类型。
- 版本。
- 内容快照。
- 来源。
- 适用范围。
- 风险等级。
- 回滚路径。

资产分层：

- prompt：影响总体行为边界和角色约束。
- playbook：沉淀可复用策略和打法。
- tool policy：规定何时查什么状态、怎么确认工具结果。
- memory：低信任参考，只能辅助，不能直接决策。

### 验证系统

验证系统开始检查资产改动是否让 T50 主指标变好。

单个 `test 1` 变好不能作为自动合并依据，只能作为候选证据。

## Phase 4：候选改进流程

目标：系统可以提出候选改进，并产生证据包。

### 记录系统

记录候选改进完整链路：

- 候选来源。
- 对应失败。
- 计划修改的资产。
- 修改内容。
- 验证计划。
- 验证结果。

### 资产系统

候选资产改动可以生成，但不直接进入主线。

每个候选都必须能回答：

- 改了什么。
- 为什么改。
- 解决哪类失败。
- 可能引入什么副作用。
- 怎么回滚。

### 验证系统

系统可以在沙盒中验证候选。

验证必须保留：

- baseline。
- candidate。
- 场景集合。
- T50 主指标变化。
- 副作用。
- 退化样例。

## Phase 5：真实失败沉淀验证集

目标：验证系统不再依赖单个存档或单次跑分。

### 记录系统

每次退化、事故、误判都要转成可复现材料：

- 场景说明。
- 起点存档。
- 触发条件。
- 相关日志。
- 期望行为。
- 失败行为。

### 资产系统

资产改动必须声明覆盖哪些能力维度。

同一类资产可以按六类能力主轴拆分管理，避免所有经验都混进一个 prompt。

### 验证系统

验证场景主要从真实失败中沉淀。

每次事故、退化、误判都变成 regression 场景。验证集随着真实运行增长，而不是一开始靠人工拍脑袋设计完整。

## L4/L5：自动合并、自动回滚、自动审计

目标：不设人类 merge 闸门。

系统成熟后，自动 merge 的最低条件是：

- 经过多场景验证。
- T50 主指标变好。
- 没有明显退化。
- 覆盖 planning、execution、memory/state、tool grounding、verification、recovery 六类维度中的相关风险。
- 资产改动可追溯、可回滚。

自动 merge 后，如果后续发现退化：

1. 先自动回滚到上一个稳定版本。
2. 再生成审计报告。
3. 把退化样例加入 regression 场景池。

审计报告必须包含完整链路：

- 候选来源。
- 验证记录。
- merge 决策。
- 退化触发。
- 回滚版本。
- 退化样例。
- 后续建议。

人类不做常规 merge 审批，只看：

- 自动审计报告。
- 异常告警。
- 回滚原因。
- 长期趋势。

## Phase 1 初版改造入口

Phase 1 初版改造方案应该单独写给 Windows Codex 执行。

它的任务边界是：

- 在 Windows 机器上的 `civ6-mcp` 仓库执行。
- 使用真实 `test 1` 单人存档。
- 允许改外部包装，也允许轻改 `civ6-mcp`。
- 先跑 3-5 回合短跑。
- 短跑后生成 HTML 验收报告并暂停。
- 人类验收通过后，再跑 T50。

它不应该承担：

- 失败归因。
- 候选策略生成。
- Replay Arena。
- 自动资产合并。
- 自动学习闭环。

## 当前优先级

当前最优先的是 Phase 1。

只有当记录系统能可靠回答“这一局发生了什么、关键决策为什么这么做、证据在哪里、存档怎么回放”之后，后续失败分类、资产体系、验证集和自动 merge 才有意义。

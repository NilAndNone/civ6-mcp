# v0.0.2 策略改进目标

`v0.0.2` 的目标是证明 `codex-hl-civ6` 不只是能记录和编排，而是能让
策略资产真实影响运行，并带来可审计的 T50 指标改进。

这版不是“新增更多入口”。它是策略改进验证版。

## 一句话目标

系统自动从正式 failure 生成候选 playbook，让候选 playbook 直接驱动
Phase 1 runner，并在 Windows Civ6 真机上用 `5 baseline T50 + 5 candidate T50`
验证侦察/扩张策略是否改善 T50 主指标。

## 输入

`v0.0.2` 的输入必须来自当前系统已经能产生的正式证据：

- 已完成的 Phase 1 T50 episode。
- Phase 2 人工确认后的正式 failure。
- Phase 4 生成的候选 playbook 改进包。
- Phase 5 被动 regression scenarios。
- Phase 3 active asset catalog。

候选不能是临时手写策略，也不能只靠人工口头指定。

## 处理过程

目标流程是：

1. 从正式 failure 自动生成候选 playbook。
2. 让 Phase 1 runner 读取候选 playbook。
3. 让候选 playbook 影响实际策略行为，优先聚焦侦察和扩张。
4. 跑 5 个 baseline T50 episode。
5. 跑 5 个 candidate T50 episode。
6. 比较 T50 主指标。
7. 生成可审计报告，说明行为差异和指标差异。

## 输出

`v0.0.2` 至少要产出：

- baseline episode 列表。
- candidate episode 列表。
- 候选 playbook 包。
- runner 读取候选 playbook 的证据。
- 行为差异报告。
- T50 指标对比报告。
- 是否进入后续 governance 的审计结论。

## 成功标准

`v0.0.2` 成功不等于“某一局看起来更好”。它至少要满足：

- 候选 playbook 来自正式 failure。
- candidate runner 行为和 baseline 有可审计差异。
- 对比样本是 `5 + 5` 个 T50 episode。
- T50 主指标至少一个关键项改善。
- 没有明显主指标退化。
- 报告能说明改进来自候选 playbook，而不是只来自随机波动或手工介入。

当前 T50 主指标沿用路线图：

- 城市数。
- 科技完成数和当前研究。
- 市政完成数和当前市政。
- 科学产出。
- 文化产出。

## 非目标

- 不以胜率作为 `v0.0.2` 主验收指标。
- 不要求 Phase 3 所有资产都直接驱动 runner。
- 不要求自动合并资产成为默认行为。
- 不要求 20+20 规模的长期实验。
- 不把单局 candidate 优势当成正式策略改进。

## 最容易错的地方

最大风险是“候选资产生成了，但 runner 没有真正读取它”。因此 `v0.0.2`
必须把候选 playbook 是否真实进入决策路径作为第一验收点。

第二个风险是“指标变好但来源不清楚”。因此报告必须同时展示行为差异和指标差异。

第三个风险是“自动化跑完了，但没有证明改进”。因此 `v0.0.2` 的核心不是
跑通流程，而是证明 playbook 驱动的策略改进。
